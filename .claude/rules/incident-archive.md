### 2026-08-26 — Live scheduler audit: Finnhub/sec-api.io broken since 08-24, 5 crashes today, run_scan blocking the 15:50 gap alert
Requested spot-check of "did today's scheduler jobs run correctly + does CLAUDE.md's Scheduler Jobs table match the code" surfaced three separate, real problems, not just doc drift.

**Doc drift (mostly already fixed by a concurrent session before this check ran):** of 4 rows checked against `scheduler_config.json`, only "Watchlist Cleanup: 08:00" was still stale — it actually runs on `market_digest_time` (09:30), no separate config key exists for it. Squeeze (12:05), Long Setups (09:35), and Alert Monitor (09:40) were already correct on disk, just not what an earlier read of this file (before this session's edits) had shown — i.e. another session had already applied the same fix mid-day. Corrected the remaining row.

**Finnhub 403 + sec-api.io 429 on every ticker, every scan, since 2026-08-24 09:44 — not a today-only blip.** `grep -c` by date: 0 occurrences 08-20 through 08-23, then 1280/927/1550 (Finnhub) and 1331/1889/928 (sec-api.io) on 08-24/25/26 respectively. Finnhub returns `403 Forbidden` (not `429`) on `/stock/transcripts/list` for every symbol — that status code usually means a plan/endpoint-authorization change, not simple rate exhaustion, and is worth checking directly with Finnhub rather than assuming it self-resolves. sec-api.io's 429 explicitly states "exceeded the free query limit of 100 requests" — the free tier is being exhausted every single day now, also starting exactly 08-24. Both fail gracefully today (caught, logged, scan continues) but add real per-ticker latency across a ~600-ticker scan.

**Scheduler crashed 5× today** (11:34, 13:30, 14:00, 14:12, 14:29, all `returncode=1` — an uncaught Python exception, not a native fault code). No traceback is visible in `logs/scheduler.log` because stderr is devnulled by the watchdog (pre-existing gap, see [[project_scheduler_logging_gap_2026_08_17]]). Stable since the 14:29 restart. A worktree named `scheduler-worker-load-issue-399d18` already exists — likely a concurrent session already investigating this; check there before duplicating the work.

**`run_scan()` (the full-universe daily scan, `scan_indices: ["Russell 2000", "S&P 500"]`, ~2,466 tickers before per-sector `max_stocks` filtering) is NOT parallelized** — unlike `scan_watchlist()`/`scan_portfolio()` (parallelized 2026-08-18, see above), the scheduler's own daily scan still scores tickers sequentially in the single `schedule`-library thread. On 2026-08-26 the 15:00 run was still executing at 16:12 (72+ minutes and counting), which meant the 15:50 Premarket Gap Alert had not fired at all by that point — `schedule.run_pending()` can't start a new job while a prior one is still running synchronously in the same thread. If a blocked job's window-gate (e.g. `_in_premarket_gap_window()`) has already closed by the time control returns to it, it silently skips for the day rather than firing late — a missed check with no error logged. The elevated per-ticker latency from the Finnhub/sec-api failures above is a plausible contributor to today's runtime being long enough to cause a collision, but this is a structural gap (one long full-universe job can starve every job scheduled after it) independent of any single day's API health.

Ordered chronologically. This is the project's institutional memory for *why* something is built the way it is — root causes, exact numbers, and (for the short-position family) an explicit note to future incidents. Routine mechanical fixes from the 2026-05/06 hardening sprints are **not** re-listed here; their outcomes are current-state facts in the sections above, and the sprint-by-sprint detail is recoverable via `git log -- CLAUDE.md` if ever needed.

### 2026-08-02 — Exit Strategy Implementation
Forward-signal data showed BUY win rate 55.8% but avg win +5.03% vs avg loss −6.38% — near-zero expectancy. Root cause: all 42 open positions had 0 active bracket legs (TIF=DAY expired every night). Fixed: bracket legs → GTC; added `modify_stop_order()`, ATR trailing stops (2.5×ATR/1h, every 15 min, never lowers), time stops (>15 trading days + |pnl|<3%, every 4h), tiered exits (T1 +7%→sell 40%+move stop to breakeven, T2 +14%→sell 50% of remainder), score-deterioration exit (score drop ≥15pt + current <55 + pnl>-3%). This sprint is also where the exit-routing bug below originated.

### 2026-08-03 — Root Cause of the Shorts (runaway tiered exit)
The IBKR Activity Statement settled it: no Transfers section exists — every short came from **executed SELL orders**, 55,687 shares of them that `order_log` never recorded. Mechanism: `_check_tiered_exits` called `place_limit_order()` **before** advancing `exit_tier` and before writing `order_log` — nothing suppressed a re-fire, nothing recorded it. A tight resubmission loop at the open (BMY: 224 identical −34-share executions in the same second; IT: 242 identical −14-share executions) kept selling the same 40%-of-position slice over and over until the position crossed zero, at which point the (then-existing) short filter in `sync_positions()` erased it from view entirely.

**Fix:** all three exit paths (time stop, tiered exit, score deterioration) now route through `order_manager.submit_exit()`, which enforces the pause + `shares ≤ held − already-working` + order-log-before-broker-call, in that order. `tests/test_exit_routing.py` replays the incident: 224 identical T1 submissions on an 86-share position now produce exactly 3 broker calls totalling 86 shares, 221 vetoed, plus a source-level tripwire that fails if any exit function reintroduces a direct `place_limit_order()` call.

### 2026-08-03 — Anti-Pyramiding & Alert Flood
Live trading produced 9 `combined_buy` signals for different tickers within 4 minutes, generating 27 Telegram messages (3 per trade). Existing long positions were also receiving new BUY orders on repeat flips — pure pyramiding, no portfolio-level cap. Confirmed duplicates in `order_log`: CALM ×4, PNW ×3, FUBO/NTST/ONB ×2. ### 2026-08-04 — Pre-Live Safety Hardening
3-agent audit before switching to live IBKR trading; 10 fixes across sizing (`portfolio_value` was hardcoded $100k), SELL sizing (now always closes the full position, not a risk-sized partial), zero-NLV fallthrough, paper→live daily_pnl transition guard, BUY signal hours tightened to 09:30 ET (SELL stays 04:00–20:00 so exits are never suppressed pre-market), order-before-place ordering for time stops / score deterioration / tiered exits, and dedup checks against in-flight SUBMITTED SELLs.

**Remaining known issues at the time** (kept as an explicit record — mitigated by the bracket STP, not fully closed): `modify_stop_order()` ambiguity with multiple STPs per ticker; `record_fill()` non-idempotency on duplicate fills; a narrow sub-hour-restart window where a `bars_ago==1` flip could replay before dedup is established; bracket stop-leg rejection rollback being dead code in practice (`ib_async` reports it asynchronously). Both non-idempotency and the STP ambiguity are still open — see backlog.

### 2026-08-05 — Live-Readiness Audit: no measurable alpha
Pre-live forensic audit of paper trading. **Headline finding: `combined_buy` has no statistically detectable alpha.** 145 matured BUY signals vs SPY over identical holding windows — 7d excess **−0.20%** (t=−0.26), 14d **+0.40%** (t=+0.41), 30d **+2.14%** (t=+1.15). No horizon reaches |t|>2; beat-SPY rate 49.7%/55.6%/54.4%. The reported 55.9% win rate was never benchmarked — it was measuring market beta, and `run_forward_digest` still only reports raw win rate.

Five silent execution defects fixed: (1) startup reconciliation was marking every SUBMITTED row missing from IBKR's open orders as ERROR without checking whether it had filled — now looks up broker execution history first, never destroys state; (2) `ib.fills()` is session-scoped, replaced with `get_executions()` (broker-side `reqExecutions()`) plus a 24h grace period before an unresolved order is touched; (3) `_check_time_stops()` measured from the LAST fill (`ORDER BY created_at DESC`), so every pyramid add reset the clock and no scaled position could ever age into a time stop — now `ASC` with a fallback to the earliest BUY of any status; (4) the whole exit layer was gated behind `if not queue: return 0` — a quiet scan silently disarmed every stop; (5) long-only invariant: `_pending_sell_shares()` now subtracts in-flight SELLs before sizing a new one, closing a gap where two exit paths could each size against the same stale share count.

On the apparent KSS/GTY/OMC oversell pattern in `order_log`: not conclusive at the time (corrupted ERROR rows understated purchases in the same accounting) — see [Short-Position Blindness](#2026-08-05--short-position-blindness-most-severe-defect-found), which settled it: KSS was short 13,247 shares. Of 30 bogus ERROR rows, only 7 could be proven filled by share reconciliation (CBT×2, FUBO, LCII, RRR×2, TRS) and were repaired (status only, `fill_price` left NULL — real fill prices are unrecoverable past ~24h); the other 23 involve since-closed positions and are unreconstructable.

### 2026-08-05 — Short-Position Blindness (most severe defect found)
**The account held 14 real short positions worth −$2.37M against an $853k NLV, and not one existed in `ibkr_positions`.** Unrealized loss on them ≈ −$121k. This is a long-only bot. Root cause, one line in `sync_positions()`:
```python
# Skip short/phantom positions — we never intentionally short;
# negative shares are paper-account artifacts from pre-position-gate era.
positions = {t: d for t, d in positions.items() if d.get("shares", 0) > 0}
```
The comment's assumption was false. Dropping the rows before the upsert meant the follow-up `DELETE ... WHERE ticker NOT IN (...)` treated them as closed — invisible to every veto layer (all keyed on `shares > 0`), `/positions`, `alert_monitor`, any audit. Explained the same-day NLV anomaly ($1,035,074 → $853,301 with a visible long book of only $178k) and settled the KSS question above.

Fixed: shorts are now recorded, not filtered. `_raise_short_alarm()` — a short in this long-only bot halts trading (`set_paused(True)` re-applied every cycle) and sends a Telegram alarm throttled to 1/6h, but **deliberately never auto-covers** — unwinding is a human decision. `get_current_exposure()` is long-only by contract (returns 0.0 for a short, so the SELL veto can't be tricked into "there's something to sell"). Layer -1 uses `exposure <= 0` rather than `== 0` as belt-and-braces. `tests/test_short_detection.py` — 10 tests.

**Operator action this did not cover:** the 14 existing shorts had to be closed manually in TWS — the code prevents recurrence and forces a halt, it does not unwind an existing book.

### 2026-08-05 — Trigger Backtest
`src/trigger_backtest.py` — the validation capability the project lacked: forward paper trading at ~65 signals/month can't resolve an edge below ~1%/trade in under a year. Replays the exact production trigger (`trend_series()` mirrors `supertrend.py` line for line, tested bar-by-bar) over ~3 years of hourly bars (`python run_trigger_backtest.py --tickers 250`, ~90s).

**Result — 17,810 flips, 242 tickers, 2023-09..2026-07, excess vs IWM:** 7d clustered t=+1.31 (no edge) · 14d t=+1.58 (no edge) · 30d t=+2.27, mean +0.70% (marginal). Naive t-stats are inflated by overlapping holding periods — always use the clustered figure. **The edge exists only at ~30 days and the system exits in days** — it harvests where there's nothing and exits before where there's something.

Entry filters do not help: `close>SMA50` looked best naively (t=+4.42) but *underperforms* the unfiltered trigger under strict treatment (t=+1.52 vs +2.27). Do not add SMA200/RSI/regime/price/ADV filters. Regime split: above SMA200 +0.62% (t=5.02), below SMA200 +0.13% (t=0.34) — no edge in a falling tape. **Survivorship bias is the largest unquantified weakness** — the universe comes from `scan_results` (tickers the bot scanned in 2026) replayed to 2023; delisted names are structurally absent. Treat +0.70% as an upper bound.

### 2026-08-05 — Exit Simulation (supersedes the horizon result above)
`run_exit_simulation.py` — bar-by-bar replay under competing exit policies (pessimistic fills: gap-through-stop fills at the open; stop-before-target on same-bar touches).

**The +0.70% horizon edge does not survive contact with a stop.** Regime A (live: Supertrend flip exit) lands at **+0.00% excess (t=0.04)**, independently reproducing three months of live near-zero expectancy — the strongest calibration evidence available. Every stop-carrying regime lands at zero or negative excess; the only positive variant (no stop, 30d time) isn't tradeable (unbounded single-name loss) and isn't significant (t=1.63). Two methodology bugs were found and fixed in producing this, both of which had *inverted* the answer before the fix: stops were sized from hourly ATR instead of production's daily ATR (several times tighter, false "stops destroy the edge" signal); and non-overlap clustering was spaced by the *current* trade's holding period, preferentially admitting fast losers (Regime A's true +0.00% was initially reported as −1.03%). Both are pinned by `tests/test_exit_simulation.py`.

### 2026-08-11 — order_log phantom-balance repair (ghost shorts, RMD, SPSC)
Follow-up cleanup after the 2026-08-03/05/06 incident family: `_check_time_stops()` in `src/ibkr_worker.py` walks `order_log`'s FILLED BUY/SELL rows chronologically per ticker to find the current holding period's start, resetting whenever the running share count returns to ≤0. Several tickers had a short-sell-and-manual-TWS-cover (from the 8/5-8/6 incident response) or another untracked closing event that was never written to `order_log`, so the walk still anchored to a stale pre-incident BUY — exactly the mechanism that fired an incorrect 17-day "zombie" TIME STOP on EVER. ### 2026-08-12 — Resting Stop/Target Left Oversized After a Partial Exit
Fourth distinct mechanism (after 2026-08-03, -05, -06) that put the long-only bot into a short — each prior incident was patched narrowly for its own trigger instead of the real invariant: **a resting SELL order must never exceed the position it protects.** `_cancel_unbacked_sell_orders()` (added 2026-08-06) already checked this but only acted when `held<=0`; when `0<held<qty` it logged a warning and left the order in place, reasoning that cancelling would strip real protection — half right, but leaving it oversized was just as wrong.

**SENEA, 2026-08-10/11:** bracket BUY 70sh filled; T1 (+7%) sold 40%=28sh via a separate order and moved the STP to breakeven via `modify_stop_order()` — which only ever touches `auxPrice`, never `totalQuantity`. The STP stayed resting at qty=70 against a 42sh position; every cycle logged the warning and did nothing. A routine disconnect/reconnect gap let the stop fill for the full 70sh, flipping the account to **-28sh** — exactly the T1-sold amount, same signature as 08-06. The 08-05 short-alarm guard caught it on the next sync and paused trading (stayed paused across a worker restart; no BUYs submitted while paused — the safety net held). Paper account only, no real money at risk.

**Fix:** `resize_sell_orders(ticker, max_qty)` caps every resting SELL (STP or LMT) at the actual held quantity, in-place (same orderId). `_reconcile_resting_sell_orders()` (renamed from `_cancel_unbacked_sell_orders`) now resizes when `0<held<qty` instead of only logging. `tests/test_unbacked_sells.py` — 12 tests, replays SENEA exactly plus the both-legs-oversized case.

**Structural note for future incidents in this family:** if a fifth mechanism surfaces, prefer strengthening `_reconcile_resting_sell_orders` (the one place this invariant is enforced) over adding another narrow guard wherever it triggered.

### 2026-08-16 — Premarket Gap Alert data source was silently broken (yfinance → Massive/Polygon)
Follow-up investigation found `scan_premarket_gaps()` (added 2026-08-15) was **non-functional in production from day one**: yfinance's `prepost=True` intraday download always reports premarket volume as exactly **0**, confirmed across 6 independent real historical ticker/day cases pulled from this project's own `watchlist_alerts` table (NMAX, TKNO, STIM, FRMM, GO, CALM — including CALM, a liquid $80+ mid-cap, ruling out "only illiquid microcaps" as the explanation). Since the function's whole design gates on `premarket_dollar_volume >= min_premarket_dollar_volume`, the filter could never pass and the alert simply never fired, silently.

Two free alternatives were evaluated and both also failed: Alpaca's free/IEX-feed tier returns **zero bars at all** before 09:30 ET (not even zero-volume bars — the data isn't requested/returned at that tier); EODHD's free tier returns HTTP 403 ("Only EOD data allowed for free users") for any intraday request. Massive/Polygon (Polygon.io's Oct-2025 rebrand) was the only source that worked, verified against a real paid "Starter" account (`MASSIVE_API_KEY`, $29/mo, 15-min delayed — acceptable since this check runs well before the open, not real-time-critical) across the same 7 cases, including a negative control: WEST on 2026-07-27 correctly came back with **0** premarket volume (proving the source reports true zeros, not just "always something").

`scan_premarket_gaps()` was rewritten to call Massive/Polygon per-ticker (`/v2/aggs/ticker/{ticker}/prev` for prior close, `/v2/aggs/ticker/{ticker}/range/5/minute/{date}/{date}` for premarket bars — Polygon has no batch endpoint, unlike `yf.download`), fanned out via `ThreadPoolExecutor` (mirrors `catalyst_scanner.py::fetch_sec_8k_events`'s pattern), with a one-call preflight key check (fails fast on 401/403 instead of attempting ~5,000 doomed requests) and per-ticker failure isolation (one ticker's fetch error no longer aborts the whole scan, unlike the old shared-batch-call model). `scan_opening_prints()` was deliberately left untouched — it uses yfinance regular-session (not premarket) data, separately verified accurate, so there was no reason to add paid-API cost there. **Timestamp handling note for future maintainers:** Polygon/Massive bar timestamps (`t`) are Unix milliseconds in UTC, not ET — every bar must be explicitly converted (`tz=timezone.utc` then `.astimezone(ET)`) before any time-of-day boundary check, or the premarket window filter silently admits/drops the wrong bars.

### 2026-08-18 — Premarket Gap Alert crashed the entire scheduler process (native heap corruption)
The 15:50 IL Premarket Gap Alert run silently never completed: `logs/watchdog.log` shows `Scheduler crashed (returncode=3221226356)` at 15:56:42, 6m35s after `scheduler.log` logged "Premarket gap alert: scanning 2463 tickers" — and no completion line ever followed. Windows Event Viewer (`Get-WinEvent`, Application log, "Application Error" source) pinned the exact fault: `python.exe` crashed in `ntdll.dll` with exception code `0xC0000374` = `STATUS_HEAP_CORRUPTION`. This exact signature had never appeared before in the crash history (checked back to April) — every prior crash was `0xFFFFFFFF`/`-1` (a deliberate `Stop-Process -Force` restart, e.g. every code deploy in this file's recent entries), plain `1` (an ordinary uncaught Python exception), or one of a few other codes from May, before `gap_scanner.py` existed. Because a native heap-corruption fault is fatal at the OS level, **no Python `try/except` anywhere in the codebase could have caught it** — it took down the whole process, not just the gap-scan job, for the ~24s until the watchdog auto-relaunched it (attempt #7). By the time it came back, `schedule`'s `next_run` for the 15:50 job had already rolled forward to tomorrow, so today's scan neither completed nor sent a Telegram summary, and every other background thread (momentum, supertrend, price alerts, catalyst monitor) was briefly down too — though nothing else was scheduled to fire in that exact ~24s window today, so the blast radius this time was limited to the gap alert itself.

Root cause (best available evidence, not a debugger-confirmed proof): `_massive_get()` was calling bare `requests.get()` per call with no session reuse, so the scan opened a **fresh TLS connection for every one of ~4,900 HTTP calls** (2 Massive/Polygon endpoints × 2463 tickers) across `massive_max_workers=10` concurrent threads, sustained for 6+ minutes — the kind of high-churn concurrent TLS handshake load that's a known trigger class for native heap corruption, plausibly aggravated by running on Python 3.14 (a very new interpreter with less field exposure than 3.11-3.13). Fixed by giving each `ThreadPoolExecutor` worker thread its own pooled, keep-alive `requests.Session()` via `threading.local()` (`src/gap_scanner.py::_thread_session()`) — deliberately *not* one Session shared across all 10 threads, since `requests.Session` is documented as not thread-safe. This collapses total connection churn from ~4,900 fresh handshakes to `massive_max_workers` (10) persistent ones. `tests/test_gap_scanner.py`'s 5 HTTP-layer tests updated to patch `requests.Session.get` instead of the module-level `requests.get` they can no longer reach. 620/1/0 suite, no regressions.

**Not a debugger-confirmed root cause** — this is the best-supported explanation from the evidence available (crash timing, faulting module, absence of any other concurrent activity at that pre-market hour, and TLS/connection-churn being a documented class of native-heap-corruption trigger), not a WinDbg-verified proof of the exact corrupting write. If `STATUS_HEAP_CORRUPTION` recurs after this fix ships, the next step is capturing a crash dump (`ProcDump -ma` or enabling Windows Error Reporting local dumps) for the *next* occurrence and analyzing it with WinDbg, the way the 2026-08-14 Docker/WSL2 BSOD investigation did.

### 2026-08-18 — Three dashboard pages crashing on every load (Scheduler, Market, Backtest)
A verification pass over the prior two days' fixes checked more than just the test suite — it also headlessly rendered all 11 dashboard pages via Streamlit's `AppTest` framework, which every existing test in this repo had never done. Three of eleven pages crashed on their very first render, unconditionally, unrelated to any of the prior two days' fixes and not caught by any existing test:

- **Scheduler page**: `_pages_modules/page_scheduler.py`'s "Scan times" `st.multiselect` passed `cfg.get("times", ...)` straight through as `default=` without checking the values existed in the widget's own hardcoded `_TIMES` option list. ### 2026-08-19 — Opening Range Explosion alert showed nonsensical percentages (300-700% "moves")
User-reported: the "💥 Opening Range Explosion" Telegram alert (`scheduler.py::run_opening_print_alert` → `gap_scanner.py::scan_opening_prints()`) sent 8 candidates at 17:15:57 UTC with `move_pct` of 333% to 697% (MXL, AMLX, MRNA, ALMS, STX, MU, SLS, PRAX — confirmed via `watchlist_alerts WHERE alert_type='opening_print_alert'`) — no single-day move of that size is plausible for any of these, let alone 8 at once.

Root cause: `scan_opening_prints()` calls `yf.download(tickers, period="1d", interval="1m", ...)` and reads `open_print = o.iloc[0]` (the first bar in the returned series) as "today's 09:30 print." Under rate-limiting/degraded service — the same batch that produced this alert also logged hundreds of `YFRateLimitError`s — yfinance can silently hand back more than one trading day of 1-minute bars for `period="1d"`. When that happens, `o.iloc[0]` is a stale bar from days or weeks earlier instead of today's open. For a ticker that has since rallied hard (MU, STX — both up sharply in the preceding weeks), that stale baseline is far below the current price, producing a wildly inflated `move_pct`. `dollar_volume = (c * v).sum()` had the identical exposure — summing extra days' volume alongside today's, which is why the corrupted candidates also cleared the dollar-volume filter easily. A clean re-run of the same universe minutes later (without the rate-limit storm) returned only 6 candidates, all in the sane 10-25% range, confirming the corruption was data-availability-triggered, not a permanent condition.

Fixed: both the `Open` and `Close` series are filtered to bars whose ET calendar date equals today's before any calculation — `c = c[c.index.tz_convert(_ET).date == today_et]` (and same for `o`) — so a stale multi-day-old bar can never be read as the open print, and the dollar-volume sum can never include extra days. `tests/test_gap_scanner.py::TestScanOpeningPrints::test_ignores_stale_multi_day_bar_from_yfinance` replays the incident (a stale bar 20 days before today's session, priced far below today's real open) and asserts `open_print` resolves to today's real first bar, not the stale one. **External design review (IdeaDistill panel), 2026-08-26 — Fix #1 confirmed, Fix #2's own stated rationale was internally inconsistent, resolved with direct measurement.** The panel accepted Fix #1 (LRU cache) as a definitive root-cause fix — no dispute there. On Fix #2 the panel raised a real logical objection: "not a reference leak" and "forced `gc.collect()` helps" can't both be true as originally stated — if `gc.collect()` does real work, cyclic garbage exists and is being cleared (evidence *against* "just fragmentation, not a leak"); if it does no real work, the memory improvement is placebo and Fix #1 explains everything.

The panel's framing was itself a false dichotomy — it misses a well-documented third case: pandas `DataFrame`/`BlockManager` objects have known internal reference cycles, so a DataFrame going out of scope becomes genuinely *unreachable* immediately (nothing in the program can reach it — this is NOT a leak, which by definition means something stays reachable) but isn't freed by simple refcounting because of the cycle; it waits for Python's threshold-based automatic cyclic collector, which may not run again for a while under sustained large-batch churn. Forcing `gc.collect()` right after the batch reclaims exactly that already-unreachable garbage sooner — a legitimate, standard mitigation for this specific pattern, not "managing a leak" in the sense the panel meant.

Settled with the panel's own proposed test rather than argument: instrumented both `gc.collect()` call sites (`momentum_scanner.py`, `supertrend.py`) to log their return value (count of objects actually freed) at INFO level (the live scheduler's configured log level — the initial DEBUG-level instrumentation would have been silently filtered in production and never appeared in `scheduler.log`, caught before deploy). Live-checked immediately with a direct spy on `gc.collect` (bypassing logger-level filtering entirely) across 3 consecutive real 300-ticker momentum scans: **2,024 / 2,145 / 2,130 objects freed — every single cycle, consistently, not a one-off.** This is real, substantial, repeatable cyclic-garbage collection, not a placebo — but a consistent few-thousand-object count each cycle is exactly the signature of pandas' own internal cycles being cleared, not evidence of a classic persistent leak (which `gc.collect()` could never reclaim, since a leaked object stays reachable by definition).

**Also actioned, the panel's other clearly-correct ask:** a 72-hour production soak with hourly RSS logging, since 30 minutes was too short to rule out multi-day creep. `log_scheduler_memory.ps1` (new, finds the live scheduler by command line, not a fixed PID, since it restarts on crash/deploy) registered as an hourly Windows Scheduled Task (`FinancialAgentMemorySoak`, 4-day duration) appending to `logs/memory_soak.csv`. **Not yet reviewed** — needs a follow-up session in ~3 days to read the CSV and confirm no multi-day creep; if it resumes, the panel's next-step suggestions (allocator tuning — `MALLOC_ARENA_MAX`, jemalloc — or smaller batch sizes) are the documented next move, not yet needed. With WATCH now written at full-scanner-hit frequency (hundreds/cycle vs. BUY/SELL's much lower rate) those would have been dominated/corrupted by WATCH rows: `weekly_digest()`'s main query (would have polluted `avg_return_7d_pct`/win-rate with non-trade observations, treating a WATCH row's `return>0` as a "win" the same as a BUY), `_llm_curation_comparison()`'s query (same class of bug), `record_fill()`'s "most recent row for this ticker" lookup (an IBKR fill callback could have attached a real fill price to a WATCH row instead of the BUY/SELL row it belongs to, if a WATCH row for the same ticker was recorded moments later — a real risk given the monitor threads run every 30 min), and `telegram_command_handler.py`'s `/status` "last signal" line (would almost always show a WATCH row instead of the actual last trade). All four now filter to `signal_type IN ('BUY','SELL')`. `tests/test_catalyst_event_study_watch_signals.py` pins all four with a real WATCH row present.

**Methodology upgrades** (`src/catalyst_event_study.py`, new module, run on demand — not wired into the scheduler):
1. **Abnormal returns vs benchmark** — `compute_abnormal_returns()` measures every WATCH row's return relative to a benchmark (default SPY, parameterizable) over the identical window, the same discipline `forward_signals.benchmark_excess()`/`trigger_backtest.py` already use.
2. **Cross-sectional clustering correction** — `_date_clustered_stats()` averages same-calendar-date observations (across DIFFERENT tickers) into one point per date before computing a t-stat, extending `trigger_backtest.clustered_stats()`'s exact technique (bucket into a coarser group, run the t-stat on bucket means) from its own time-axis (same-ticker overlapping holds, bucketed by month) to the cross-sectional axis (same-date across tickers, bucketed by day) — per Kolari & Pynnonen (2010). `direction_report()` reports both the naive and clustered figures per (direction, horizon); always read the clustered one.
3. **Placebo/control-date test** — `placebo_test()` compares real WATCH-event returns against random non-catalyst dates for the SAME tickers (excluding a buffer window around every real event), via a Welch's two-sample t-test. Pattern observed in `matthias-wyss/iti-8k-analysis` (GitHub), not previously done anywhere in this codebase.
4. **Documented, uncorrectable caveat** — both `record_watch_signals()`'s and `catalyst_event_study.py`'s docstrings state explicitly: Polygon's per-article sentiment is a third-party black box this project doesn't independently validate (read every result as "does Polygon's sentiment model predict returns", not sentiment in general), and an LLM-computed sentiment label on already-published news carries a theoretical look-ahead-bias risk if the underlying model's training data included the article's aftermath (arXiv:2309.17322) — unverifiable from our side, not something to fix.

### 2026-08-28 — Full-day signal-validation pass: four strategy families tested, none clear the bar; best lead is insider-conviction-conditioned entries, still unconfirmed
Same day as the entry above (that fix — the `momentum.rvol_min` liquidity-check bug — was the opening finding of this session, not a separate day). The user's actual question was broader: "is the system on the right track for live trading in 1-2 months, are we validating data properly." This entry covers everything tested after the liquidity fix.

**Headline: every strategy family tested today, using a consistent rigorous harness, failed to show a validated, holdout-surviving edge.** The harness discipline (all reused from/consistent with `src/trigger_backtest.py` and `run_signal_panel.py`, which already existed): naive (overlapping-window) stats reported alongside "tradeable" stats — real exit simulation (`simulate_exits`: 3×ATR stop, 30d max hold, 0.2% friction, pessimistic gap fills) run through `clustered_stats()` (per-ticker non-overlapping trade selection, THEN month-clustering) — plus a Bonferroni-style threshold (`2.0 + 0.55·ln(N)`) for however many candidates were compared in a given panel. A time-based dev/holdout split (first 70% of months vs. last 30%, never touched during discovery) was added ad hoc this session for every retroactive test — see the new Open Backlog item about formalizing this, it wasn't reusable infrastructure going in.

**1. Equity technical trend-following, large-cap universe (~150 tickers, `run_signal_panel.py`, existing tool, just run):** 7 candidates (`supertrend_flip` = the actual production trigger, `golden_cross`, `breakout_52w`, `donchian_20`, `momentum_12_1`, `rsi_dip_in_uptrend`, `gap_up_continuation`). Bonferroni threshold |t|>3.07. `supertrend_flip`: tradeable −0.52%, t=−0.98, win 49.2% — reconfirms the 2026-08-05 audit's "no measurable alpha" finding, 3+ weeks later with more data. Only `golden_cross` cleared the bar, and in the wrong direction (−2.40%, t=−3.43 — a confirmed *negative* performer, not a discovery).

**2. Same production trigger, genuine small-cap universe (180 Russell-2000 tickers verified to have zero S&P-500 overlap, IWM/SPY benchmark):** naive 30d excess looked tempting (+0.45-0.50%, t=2.36-2.61) but tradeable/clustered collapsed to −0.36 to −0.39%, t=−0.51/−0.68, win 47.6% — same failure pattern as large-cap. The "maybe edge hides in the less-covered small-cap tail" hypothesis did not hold.

**3. Pairs trading / stat-arb.** Found an abandoned in-house module (not in git, not in any memory file — recovered via `.claude/agent-memory/financial-agent-builder/project_pairs_trading.md`): **DSSPT** (Dynamic State-Space Pairs Trading), built 2026-04-17, manual Kalman filter for dynamic hedge-ratio beta + Ornstein-Uhlenbeck half-life estimation + DBSCAN pair clustering + VIX regime gate — a real, legitimate methodology, not a toy. Ran live for exactly one week, sent real Telegram alerts, then was deleted without ever being evaluated; left behind 94,734 raw signal rows and a `pairs_watchlist`/`pairs_signals` DB schema still present. Backtesting the leftover signals required collapsing them into true episodes first (raw rows refired every ~5-6 min per pair with no dedup/cooldown at the source) — 207 episodes, but only **5 distinct entry dates**, because 89/112 earliest episodes all first-fired within ~25 minutes of the monitor's own startup (`pairs_watchlist.added_at`) — almost certainly a cold-start artifact (static historical spread_mean/std vs. live prices at the instant the monitor switched on), not 89 real opportunities. Clustered-by-entry-date results (n=5, too underpowered to prove anything either way): 1d +1.12%/t=0.74, 5d −1.39%/t=−1.96, 10d −3.09%/t=−0.89 — trends negative beyond day 1, not encouraging, but not dispositive.

**4. PEAD (post-earnings drift), 100 tickers, 2,299 real events.** Event dates from `yfinance.get_earnings_dates()` (real report timestamps, AMC/BMO-aware), not Finnhub's free-tier `stock/earnings` endpoint (period-END date only — would misdate the event by weeks). Well-powered (51 independent months). No classic continuation drift; if anything a mild short-horizon *reversal* (3d t=−2.30, 5d t=−2.40, fading to noise by 10-60d) — opposite of PEAD's prediction, not Bonferroni-significant, but the closest thing to a non-null naive result all day. Market-cap segmentation (data-quality caveat: 1,246/2,299 rows lost to what looked like yfinance rate-limiting from a day of heavy use, only 45/100 tickers usable) did not support "smaller = more edge" — the single most negative point estimate of the day (−2.38% at 60d) was in the small/mid bucket.

**5. Retroactive catalyst-conditioned entries** (flip + fresh Massive/Polygon news within [-3d,+1d]), the most-discussed lead of the session. First attempt at the news backfill silently returned 0 articles for all 166 tickers — root cause was **not** network flakiness, it was `load_dotenv()`'s default search walking up from the *calling script's own file location* (a scratch temp dir) rather than cwd, when the script is run as a real `.py` file instead of `python -c`; every request went out unauthenticated (401) and the bare `except: break` swallowed it silently. Fixed with an explicit `load_dotenv("<project>/.env")` path — **this exact bug should be assumed to recur in any future one-off script that lives outside the project directory**, not just this one. Second failure mode, same test: two background runs (a broken retry-loop left running plus the fixed rerun) wrote to the same output CSV path concurrently; the slower-to-complete one silently clobbered the good result. **Lesson applied for the rest of the session: never launch a second backgrounded run of a script against a shared output path without confirming the first one's completion notification first.**

Once the data was actually clean: flip+any-catalyst naive-return slicing looked encouraging (30d +3.43%/t=2.01 for positive-sentiment-only, n=370) — but re-run through the REAL harness (`simulate_exits`/`clustered_stats`, not naive fixed-30d-forward returns) it collapsed to baseline-level noise (holdout t≈0.25 vs SPY, ≈0 vs IWM). The naive-vs-real gap here was the single clearest demonstration all day of why "tradeable" numbers, not naive ones, are the ones to trust — a stop-loss frequently exits before a catalyst-driven move's favorable continuation would have paid off.

**6. Exit-policy sensitivity sweep** (same entry signal throughout, only `ExitConfig` varied — the one test today NOT about the entry side): production (3ATR/30d) mean −0.37/−0.39%, t=−0.52/−0.68. Best of 7 variants: **no stop-loss at all, 30d time-exit only** — mean +0.48/+0.50%, t=+0.82/+1.43 (still nowhere near even the basic |t|>2 bar, let alone this panel's own Bonferroni threshold of 3.07). Confirms the "tradeable always underperforms naive" pattern is at least partly attributable to the stop itself getting hit before favorable moves complete — but picking "no stop" as a new default on the strength of being best-of-7 would itself be the exact overfitting trap this session kept flagging; not adopted, needs its own out-of-sample test if pursued.

**7. TradingView.** User asked whether a paid subscription + "connecting Claude to it" would help. Findings, not opinion: (a) `src/supertrend.py` already computes the identical formula TradingView's own indicator uses — a subscription produces the same signal already tested and found wanting, not a different one; (b) TradingView has no public trading API for retail plans (only one-way webhooks *from* TradingView); (c) browsed both the "Popular" and "Editors' Picks" community-script tiers live — ~19/20 top items in each are discretionary visual/pattern tools (ICT/SMC-style "liquidity sweep"/"order block"/"kill zone" indicators), several with explicit language like *"not a standalone signal"* / *"informational... all trading decisions... user's responsibility"*, not testable rule-based strategies; boost/like counts are popularity signals, unrelated to validated performance. Concluded this doesn't offer a shortcut past today's rigor — closed off as a near-term direction.

**8. Insider Form-4 conviction as an entry condition — today's strongest (still unconfirmed) result.** An external multi-model review ("DISTILL" consensus, pasted into this session mid-day) recommended insider Form-4 buying + unusual options activity over pure technical signals. Verified during planning that the two halves are NOT equally testable: `src/massive_insider_client.py`'s Polygon endpoint (`/stocks/filings/vX/form-4`) confirmed live to honor `filing_date.lte` for historical windows (retroactively backfillable, same pattern as the news test) — but `src/options_flow.py` is built entirely on `yfinance`'s *live* `option_chain()`, which has no historical equivalent; unusual-options-activity cannot be backtested retroactively with current infrastructure and would need to join the forward-collecting WATCH-layer queue instead.

Backfilled real Form-4 open-market-purchase (code "P") history for the same 166-ticker/35-month universe (2,317 buy transactions fetched). Flip + insider buying within the prior 45 days (1,393/11,494 = 12.1% of flips): full-sample tradeable +2.29%/+2.03%, t=+1.64/+1.49 (still short of this panel's Bonferroni bar of 2.60, but the best point estimate of any entry-side test today). Dev/holdout: dev t=+1.78/+1.84 → holdout t=+0.35/+0.02 — weakened sharply but the **sign held and win rate actually improved** (49.1%→57.3%), unlike the catalyst test's collapse to ~zero. A stricter cut (2+ distinct buy transactions) looked *stronger* in dev (t=1.63-1.72) and **flipped negative in holdout** (t=−0.33/−0.66) — a live, real example (not hypothetical) of "the best-looking variant is the most overfit one," exactly the failure mode a user-supplied overfitting checklist warned about earlier in this same session.

First-ever use of `run_backtest()`'s already-captured-but-never-exercised `spy_bull` column (from `market_regime.py`'s SPY-vs-SMA200) to slice results by regime: baseline is negative specifically in bull regimes (t=−0.72/−0.87) but positive when SPY is not above its SMA200 (t=+1.03/+0.88, win 58.2%); insider buying turns bull-regime baseline positive (t=+1.51/+1.41). The single most extreme cell (2+ buys, non-bull regime: mean +15%, t=1.89) rests on only 51 clustered units across 6 months — flagged explicitly as needing an outlier-concentration check (not yet built, see Open Backlog) before being trusted at all; a 6-month regime population is not enough to draw a conclusion from regardless.

**Also added during this session, purely as documentation/methodology hygiene, not a code change:** a user-supplied overfitting-avoidance checklist (train/test splits, purged CV, multiple-testing correction, sensitivity analysis, realism, forward-testing) was audited point-by-point against what actually exists in this codebase. Real gaps found and added to Open Backlog: no purged/embargoed cross-validation or Deflated-Sharpe/SPA-test-level multiple-testing correction (only the simpler Bonferroni bound); no persistent cross-session trial-count log; survivorship bias in every `get_index()`-driven backtest universe (current constituents only, not point-in-time historical membership — likely makes today's already-null results *optimistic*, not pessimistic); no Monte Carlo/bootstrap of trade sequences and no transaction-cost sensitivity sweep (one fixed 0.2% friction throughout, likely an underestimate for thin small-cap spreads); no standing outlier-concentration or regime-slice check before today. None of these invalidate today's findings — if anything the missing checks (survivorship, cost sensitivity) point toward today's numbers being flattering, not unfair, to every tested strategy.

**Net assessment for the original question ("are we on track for live trading in 1-2 months"): no.** Infrastructure, data collection, and risk management are sound — the open question was always the entry signal, not the plumbing, and that question is now answered "not yet, across four independently-tested families" rather than merely assumed. The one candidate that didn't fail outright (insider-conviction-conditioned entries) directionally survived a genuine holdout but is far from statistically confirmed and rests partly on a 6-month regime sub-population. Recommended gate before any live-capital decision (consistent with the DISTILL consensus and this session's own methodology): a Bonferroni-corrected clustered t-statistic clearing the panel's threshold, on a genuinely out-of-sample holdout, across ≥100 independent clusters, with win rate meaningfully above 50% after realistic friction — not yet met by anything tested. See Open Backlog for the concrete next steps this pass left queued (formalize the holdout-split helper, outlier-concentration check, options-flow forward-collection, more insider-conviction history).

### 2026-08-29 — Tunnel churning a new public URL roughly every minute, for 27+ minutes straight
User report: "משהו לא תקין עם הtunnel של cloudeflare, אני כל דקה מקבל לינק חדש" (new link every minute). `logs/dashboard_tunnel.log` showed a clean, single-watchdog restart loop, not a duplicate-process race: every ~70s, `run_dashboard_tunnel.py` started, got a tunnel URL, sent it to Telegram, then logged `Streamlit exited (code 1), shutting down tunnel` within 10-15s — 23 consecutive cycles from 19:31:37 onward.

**Root cause: an orphaned Streamlit process, not a code bug.** At 19:31:37 the previous night's Streamlit (running fine since the prior evening) died with `exit code -1` (`4294967295` unsigned — killed from outside, not a normal exit). One second later a *different* Streamlit process appeared bound to port 8501 and kept running successfully for 29+ minutes, completely outside the watchdog's process tree (its own parent PID was already dead by the time this was investigated — a classic orphan). Every subsequent watchdog-driven cycle's own freshly-spawned Streamlit then failed to bind the already-occupied port and exited(1) within ~10-15s; `run_dashboard_tunnel.py`'s main loop reads that as `streamlit_proc.poll() is not None` and — with no distinction between "crashed" and "port stolen" — tears down the tunnel and lets the watchdog restart everything, including a brand-new public URL, every cycle. The likely mechanism for the orphan itself: `start_streamlit()`'s `subprocess.Popen(..., creationflags=CREATE_NO_WINDOW)` has no console at all, so if its parent (`run_dashboard_tunnel.py`) is interrupted by something that relies on console signal delivery (Ctrl+C, closing a terminal window), the child never receives it and survives indefinitely.

**Diagnosis process, because the fix depended on ruling out the obvious wrong answers first:** `start_streamlit()` doesn't capture Streamlit's stdout/stderr at all (inherits a `CREATE_NO_WINDOW` parent's handles), so there was zero traceback to read — every plausible code-level cause had to be tested by direct reproduction instead: (a) manually ran `dashboard.py` standalone on a spare port — stable; (b) loaded the Market page specifically (the day's other change, the new Fear&Greed widget) via a real browser session against that manual instance — rendered correctly, no crash; (c) reproduced `start_streamlit()`'s exact `Popen`/`CREATE_NO_WINDOW` pattern from a console-less `pythonw.exe` parent — stable 30s; (d) stood up a real cloudflared quick tunnel against a manual instance, exposing it to the actual public internet — stable for minutes. All four came back clean, which is what pointed at process/port state rather than application code. Killing the identified orphan (PID confirmed via `Get-NetTCPConnection`/`Get-CimInstance Win32_Process` command-line match, with the user's explicit go-ahead before terminating anything) didn't fix it *immediately* — 2-3 more cycles still failed for another ~3 minutes, consistent with Windows needing time to fully release the port's socket state after a forced kill of a listener with active client connections (the various short-lived cloudflared instances had all been proxying to it). Stable from 20:04:44 onward.

**Fix (`run_dashboard_tunnel.py`):** `start_streamlit()` now calls `_clear_stale_port(STREAMLIT_PORT)` before every launch — finds whatever PID (if any) is LISTENing on the port, and only if its command line positively matches our own `streamlit`+`dashboard.py` invocation, `taskkill /F`s it; an unrecognized occupant is logged and left alone rather than killed blind. No new dependency (psutil isn't in this project) — shells out to `Get-NetTCPConnection`/`Get-CimInstance Win32_Process` via PowerShell, same style as other Windows-native process handling in this codebase. Streamlit's stderr is now redirected to a rotating `logs/streamlit_stderr.log` (10MB×5 backups) instead of being silently inherited-and-discarded, mirroring `run_scheduler_watchdog.py`'s `_open_stderr_log` fix for the same class of blind spot (see the 2026-08-26 entry above). Both helpers verified directly against the live PID/port at the time (read-only detection calls only, never the kill path, against production while it was up).

**Deployment note:** unlike `scheduler.py`, `run_tunnel_watchdog.py` re-invokes `run_dashboard_tunnel.py` as a fresh `subprocess.run([PYTHON, str(SCRIPT)])` every single cycle, re-reading the `.py` file from disk each time — no long-lived import to restart. Once this fix is merged from the worktree branch into the live checkout, it activates automatically on the *next* natural restart cycle, with no explicit watchdog restart required.
